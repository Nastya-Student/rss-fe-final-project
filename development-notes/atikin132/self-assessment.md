## Описание работы

В рамках командного проекта я отвечал за настройку инфраструктуры проекта, реализацию клиентской архитектуры, разработку страницы dashboard, создание сервисного слоя, а также разработку и интеграцию системы виджетов (Widget Engine) и нескольких интерактивных виджетов.

### Настройка проекта и инфраструктуры

На начальном этапе я полностью настроил конфигурацию проекта. В работе использовал **TypeScript**, **Vite**, **ESLint (Unicorn)**, **Prettier**, **Husky** и **Commitlint**. Также дополнительно реализовал кастомную проверку коммитов через собственное правило для Commitlint, чтобы обеспечить строгий формат сообщений коммитов.

Кроме того, я настроил:

-   единый стиль именования веток и коммитов,
-   автоматическую валидацию названий веток (validate-branch-name),
-   pre-commit хуки через Husky.

Это помогло стандартизировать процесс разработки в команде.

----------

### Архитектура и базовый функционал

Я реализовал **роутинг приложения**, используя hash-based подход. Это решение было выбрано осознанно, чтобы избежать проблем с деплоем (например, на GitHub Pages).

Роутинг поддерживает:

-   статические страницы (landing, login, dashboard и др.),
-   динамические маршруты (`practice/:topicId`),
-   обработку невалидных URL (страница 404).

Также я предложил команде и использовал сам собственные утилиты для создания DOM-элементов, что ускорило разработку и обеспечило переиспользуемость кода.

### 2. Widget Engine

Widget Engine отвечает за:

- рендеринг различных типов виджетов,
- обработку пользовательских ответов,
- управление последовательностью виджетов (сессией),
- отображение результатов.

Я реализовал Widget Engine с использованием паттерна Strategy, что позволило:

- изолировать логику каждого виджета,
- избежать громоздких `switch/case`,
- и если понадобится добавлять новые типы виджетов, то это будет сделать проще.

У каждого виджета есть свои тип (`type`) и данные (`payload`).

Для каждого типа виджета была реализована стратегия, в которой есть методы `render()` - отрисовка виджета и `validate()` — проверка ответа.

Большие проблемы возникли с типизацией. В методе `render()` появлялись ошибки из-за типа `never`. За решением этой проблемы я обращался к ИИ, и через очень много итерации добился рабочего варианта.

Работает Widget Engine следующим образом:

1.  Принимает массив виджетов (сессию),
2.  Рендерит текущий виджет,
3.  После ответа:
    -   валидирует его,
    -   показывает результат,
4.  Позволяет перейти к следующему виджету,
5.  После завершения — отображает экран результатов.

В последствии я улучшил Widget Engine:

1.  Добавил ограничение в 10 виджетов за раз, потому что раньше показывались все виджеты по теме.
2.  Сделал user progress, который показывает пользователю, сколько виджетов он уже решил, как решил, текущий виджет, и сколько виджетов ещё осталось.
3.  Исправил баги в виджетах.

  
Код: [PR#27](https://github.com/Nastya-Student/rss-fe-final-project/pull/27), [PR#77](https://github.com/Nastya-Student/rss-fe-final-project/pull/77)

  

### 3. Async Sorter Widget

Этот виджет моделирует работу event loop в JavaScript и требует от пользователя правильно распределить вывод `console.log` по контейнерам.

Пользователю отображается блок кода с `console.log` и зоны (Call Stack, Microtasks и Macrotasks).

Пользователю нужно перетащить элементы в правильные зоны и получить корректный порядок выполнения.

Async Sorter работает следующим образом:

1.  Парсинг кода: строка из моковых данных разбивается на массив и извлекаются значения из `console.log`.
2.  Drag and Drop: изначально пробовал HTML Drag and Drop API и Dragula, но столкнулся с проблемами (особенно на мобильных устройствах), в итоге использовал библиотеку SortableJS.
3.  Сбор ответа: реализована функция `getAnswer()`, которая проходит по всем drop-зонам, собирает элементы в структуру ответа, формирует итоговый порядок (output).
4.  Валидация в Async Sorter Stratege: сравнение ответа пользователя с эталонной структурой, проверка порядка и содержимого.
5.  Визуализация выполнения: добавлена кнопка Run, при нажатии на которую вывод очищается и элементы появляются с задержкой (имитация выполнения кода в соответствии с выбором пользователя).

Код: [PR#34](https://github.com/Nastya-Student/rss-fe-final-project/pull/34)

  

### 4. Quiz Widget

Пользователю показывается вопрос, затем он выбирает ответ и отправляет его, и показывается результат (правильно или нет).

Для реализации этого виджета нужно было изменить моковые данные, чтобы хранился не индекс, а сам правильный ответ, потому что я хотел, чтобы каждый раз массив с вариантами ответов перемешивался. 

Как и в других виджетах после нажатия Submit ответ валидируется, отображается результат (Correct или Wrong), появляется кнопка Next или Go to Results и блокируются элементы управления.
